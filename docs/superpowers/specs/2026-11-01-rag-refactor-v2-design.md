# Shiping RAG 重构 Spec v2：自动入库、Markdown、双模式索引与混合召回

日期：2026-11-01
状态：待审阅，尚未实施。
适用范围：Shiping桌面、本机知识库管理网页与共享RAG后台。
文档关系：本文件完整取代此前《RAG重构Spec》及其召回补充；实施以本版经确认的内容为准，不拼接旧条款。

## 0. 本版结论与范围

已确认的方向：上传后自动清洗并自动增量更新；进入RAG的最终正文统一Markdown；增加知识库删除；索引分全量和增量；精简前台操作。根据用户最新选择，召回采用**先优化混合召回、去重和上下文装配，再评测reranker**的路线。

首版默认不新增reranker模型，不将其作为安装和使用的依赖。首版交付必须包含真实BM25召回、中文查询处理、排名融合、片段去重、上下文完整性和评测，召回优化独立验收，不依赖后续精排模型。

只有达到精排增强的启用条件并另行确认资源后，才进入可选reranker扩展。默认安装精排模型不在首版范围。

本轮交付物为完整Spec；不修改应用功能、安装模型、迁移或重算资料。

## 1. 目标与已确认需求

将“上传后再找清洗按钮、复核、建立候选索引”的日常流程，改为上传后自动完成处理。用户主要管理资料和知识库，后台负责数据质量与索引一致性。

用户明确要求：

1. 精简冗余实现及前端入口，不重写与本次无关的屏幕问答、语音或模型设置功能。
2. 文件上传后后台自动解析和清洗，不需要正常情况下点清洗按钮。
3. 所有进入 RAG 的最终正文统一为 Markdown，再按文档结构分块、向量化。
4. 增加知识库删除方式。
5. 建立索引明确区分全量与增量。
6. 先交付 Spec，后实施。
7. 正常资料清洗成功后自动增量更新索引，只有失败或质量异常时才提示处理。
8. 召回先采用基础优化方案，本地reranker后续评测、可选启用。

以下细节为本 Spec 的设计建议，随本文一起审阅，并非用户此前逐项确认：知识库删除默认可恢复；内置 Shiping 资料库保留容器；全量索引不等于重新 OCR；初次升级受控转换既有资料。

## 2. 当前代码事实与重构原因

| 当前实现 | 存在的问题 | 重构方向 |
| --- | --- | --- |
| ProcessingJobs 解析完成进入 review，apply 后才启用 | 正常资料也被迫手工操作 | 正常结果自动进入索引队列，异常才进入人工处理 |
| cleanPages 输出带页标题的正文，另有各格式解析器 | 还不是统一的 Markdown 结构协议，页标题会干扰章节分块 | 统一格式转换、规范化与位置映射 |
| library/generations.ts 遍历整个知识库，所有片段重新 embed | 当前 v3 增量触发仍相当于重建，耗时随全库增长 | 按变更计算差集，保留未变向量 |
| 桌面 service.ts、网页 vectors.ts、jobs.ts 各自调度 | 跨进程重复构建、状态不一致与维护成本 | 单一后台任务调度，桌面和网页只提交指令 |
| v2 JSON 索引与 v3 SQLite 代际并存 | 多套状态和分支 | 旧路径仅用于受控迁移；迁移完成停止双轨生产读写 |
| projects 只有创建、读取，没有删除生命周期 | 知识库无法移除 | 知识库回收站、恢复和受控永久删除 |
| “处理与清洗”是独立主导航，索引页还有重叠功能 | 入口分散，用户难以理解 | 以资料列表为主，任务状态与异常详情就地展示 |

依据文件：src/main/document-processing/{jobs,quality}.ts、src/main/library/{repository,generations}.ts、src/main/rag/{service,chunks,structure}.ts；相邻 local-rag/web/{server,store,vectors}.ts。

### 2.1 当前召回事实


- BGE-M3将问题转向量，Chroma按余弦距离召回最多24个片段；rankHits中语义候选有固定0.45相似度门槛。
- 另扫描有效片段做关键词命中，候选内用BM25式公式排序。IDF和平均长度来自本次候选集合，未建立基于有效语料统计的独立全文倒排召回。
- 采用RRF排名融合，再叠加关键词、人名与网址规则；这不是独立reranker模型精排。
- 最多6片进入生成上下文，共享6000字符预算；当前会按字符直接截断，可能破坏句子、代码或表格。
- 对话query主要取最近两条用户消息、简单过滤语音口头词并补少量指代上下文；只有截图且无文字时不执行文本知识库检索。
- v2与v3召回实现仍有重复。重构应统一语料过滤、查询处理、候选和最终上下文装配，而不是两套路径分别调参。


## 3. 总体架构与方案选择

保留 Electron、Node 后台、SQLite、Chroma、Ollama/BGE-M3及本地 OCR，不引入新的数据库服务器、云端清洗或大型模型。

采用：**单一后台流水线 + SQLite 版本与任务主记录 + 不可变向量条目 + 活动清单切换**。

不选择直接在当前活动索引上覆盖、删除向量的方案：虽然改动较小，但构建中断可能使正文与向量错配，无法保留当前服务版本。也不选择每次增量都复制全库到新集合的方案：它减少 embed 计算却仍全量写向量，不能满足这次减少冗余的目的。

正常路径：

```text
上传文件 / 新建或编辑 Markdown
  → 保存原件或人工修订、登记任务
  → 文件检查与解析（必要时本地 OCR）
  → 保守清洗与统一 Markdown
  → 质量检查
       通过 → 结构分块 → 自动增量索引 → 校验 → 原子启用
       异常 → 记录问题 → 资料行显示“需处理” → 修正或重试
```

- 原件和资产保存在受控文件目录；不覆盖原件。
- SQLite 是资料版本、最终 Markdown、来源映射、任务、分片清单和活动指针的唯一事实主库。
- Chroma 只保存派生向量条目，不负责资料生命周期和任务状态。
- 最终 `.md` 文件按修订导出，文件可重复生成；不维护一份可独立编辑的 Markdown 文件与 SQLite 双主库。
- 所有文件解析、OCR、分块和向量计算仍在本机。生成回答继续沿用用户配置；本地处理不代表云端回答也离线。

### 3.1 草稿与已启用版本

资料分别记录待处理/人工编辑修订与已启用修订。保存编辑只创建新修订，不立即替换检索或全文上下文所用的已启用MD。候选构建成功时在同一SQLite事务里切换启用修订和索引清单；失败则保留草稿便于重试，同时继续使用旧启用修订。新资料尚无启用修订时不参与回答。

删除、禁用和项目删除不等待草稿激活，按当前管理状态立即过滤；检索的正文匹配检查使用活动清单内的已启用修订，不能因为存在更新草稿就误将旧启用版本过滤掉。

### 3.2 单一后台所有者

将当前管理服务中的后台能力整理为共享 library-service：网页是其一个入口，桌面也通过本机 API 读写资料并提交任务。OCR 子进程继续复用；不再让 Electron 和网页分别维护索引队列。

任务先写入 SQLite，再返回 jobId；用事务认领、有限租约、心跳和重启恢复防止重复执行。同一知识库一次只有一个索引写任务，全量与增量也遵守这一约束。

后台服务未运行时，桌面显示“本地知识库服务未运行”，保留当前可用资料与配置，不悄悄转回旧 JSON 写入。文档中写清启动依赖；不新增开机启动项。桌面全文模式也通过同一服务获取已启用 Markdown，避免形成第二套编辑入口。

## 4. 自动处理与 Markdown 协议

### 4.1 文件入口与重复处理

保留现有 PDF、DOCX、Markdown、TXT、PNG/JPG/JPEG/WebP、XLSX、PPTX 支持范围和资源限制。

- 同知识库原件哈希、解析/清洗/Markdown规则版本一致：复用已有处理结果；已建立索引时不重复向量化。
- 同文件名但内容不同：不能仅凭名称覆盖。明确“替换此资料”才成为该资料的新修订；普通上传作为新资料或提示已有同名项。
- 同哈希资料在回收站：提示恢复或重新导入，不能默默恢复。
- 手工编辑 Markdown 走规范化、质量检查和索引，不重新 OCR，也不覆盖人工修订。
- 用户修改结果必须有父修订和版本冲突检查。对已人工修改资料重新解析原件，必须明确使用“重新解析原件”，先提示新版本会替换人工内容；构建成功前仍保留旧版。

### 4.2 清洗内容

自动执行可解释、可重复、不会改写事实的规则：换行与控制字符规范化、基于位置和多页证据的重复页眉页脚清理、保守续行合并、原生文字与OCR明显重复去除。

保护标题、段落、列表、数字、URL、代码缩进和表格行列。禁止全库按句子去重、无条件删除空格、让大模型润色正文。记录规则版本、变更摘要和来源，不要求用户逐项批准日常安全修改。

警告分级：

- 信息：如成功移除重复页眉，可自动继续。
- 非阻断警告：信息无明确损失，例如页面使用OCR但未发现异常，允许自动继续并在详情提示核对。
- 阻断异常：漏页/页面解析失败、有效正文为空、大量异常字符、无法可靠恢复的重要表格/复杂阅读顺序、OCR疑似严重遗漏等，进入“需处理”，不以部分结果冒充完整结果。
- OCR 无置信度数据时显示“未提供”，不能虚构分数；质量检查只能发现已知问题，不能保证发现所有语义错误。

首版保守将疑似复杂版面、未解析信息图片、超过识别数量上限等现有警告映射为阻断异常；成功OCR本身不阻断。阈值和代码到等级映射必须版本化并用样例验证，不能由界面随意忽略。

### 4.3 统一 Markdown 规则

所有索引入口只接受版本化 canonical Markdown；解析器不能各自直接把普通文本送入 embedding。

| 来源 | 最终 Markdown 表达 |
| --- | --- |
| PDF / 扫描PDF | 标题、正文、列表；页码保存在来源映射中，不把“第N页”统一生成为一级章节 |
| DOCX | 标题层级、段落、列表和可恢复表格 |
| Markdown / TXT | 保留合法结构；纯文本按段落整理，不臆造层级 |
| 图片 | OCR段落及图片来源引用，缺乏证据不臆造标题 |
| XLSX | 工作表标题、表头及数据表；合并格/公式缓存缺失明确标记，不执行公式 |
| PPTX | 幻灯片标题、正文/列表、备注与图片文字；保留页序来源 |

标准要求：UTF-8、LF换行；保留围栏代码；可靠简单表格使用 Markdown，无法无损表达的合并单元格使用保留结构的 HTML 表格或阻断处理；图片引用使用受控相对资产地址。公式已有可靠文本/LaTeX时保留，否则保留原件定位与缺失提示，不能伪造转换成功。

文件名、修订、页码、工作表/行列、幻灯片及坐标保存在SQLite来源映射；可在导出MD的元数据与来源附录中显示，但不作为检索正文反复嵌入。人工改文后无法确定的精确位置标记未知，不能复用旧偏移。

MD导出支持单篇及知识库批量打包（附被引用资产）；原件仍按原格式下载。备份清单、内部API及SQLite结构化字段不强制变成Markdown，“统一MD”针对供RAG使用的正文与用户内容导出。

### 4.4 分块方式

采用**Markdown结构分块 + 超长单元递归拆分**，继续复用和整理现有 structure.ts，而非增加语义分块模型。

- 先按标题层级形成章节，分片继承标题路径。
- 段落、列表项、问答、代码围栏、表格为优先完整单元，避免主题混杂。
- 过长单元按段落、句子等边界继续拆；代码围栏保持合法闭合，表格按行拆并重复表头。
- 首版沿用现有目标600字符、上限1200字符、相邻重叠100字符，明确单位不是token；完整单元保护及重复表头允许受控例外，不能无限超长。
- 额外检查真实 embedding 输入长度，超模型上限继续安全拆分，不启用静默截断。参数与分块规则纳入版本。
- 每片保留MD修订、标题路径、起止范围和来源页/元素；重复表头或上下文前缀属于补充内容，不能伪装成连续原文偏移。

## 5. 全量与增量索引

### 5.1 用户看到的行为

| 操作 | 默认行为 |
| --- | --- |
| 新上传正常资料 | 自动增量处理 |
| 编辑资料正文 | 自动增量；失败保留旧启用版本 |
| 重命名、标签、启用模式变化 | 更新元数据与活动清单，embedding输入不变则0次重算 |
| 移除资料 / 知识库 | 立即阻止检索，排队维护索引，不等待向量物理删除 |
| 恢复资料 | 校验旧向量仍存在且兼容，能复用则复用，否则增量补齐 |
| 点击“增量更新” | 核对差异、补齐失败与缺失项，无变化则明确“无需更新” |
| 点击“全量重建” | 对该库所有当前有效MD重新分块、全部重新计算向量，独立构建后切换 |

全量重建使用现有最终MD，不默认重新解析/OCR原件；“重新解析原件”是资料详情的高级维护操作。模型指纹、规范化/分块版本不兼容时，增量任务标明原因并进入一次受控全量重建，不混写不同维度向量。

### 5.2 真正的增量与一致性

1. 从SQLite固定知识库目标快照，计算新增/修改/删除/元数据变化差集。
2. 对变化文档重新分块；不变化的文档不重新解析、不重新分块、不重新写向量。
3. 新片段向量使用不可变标识；embedding缓存键覆盖模型摘要/维度、预处理版本和实际embedding输入的哈希。完全相同输入可复用计算结果。
4. 逻辑片段ID关联修订和位置；物理向量ID与内容输入绑定，不使用整篇文档revision作为所有向量的失效依据。这样修改一段不会强制计算所有未变片段。标题路径参与embedding时，标题变化影响其后相关片段。
5. 同一知识库、同一配置空间内，增量只追加所需新向量；新活动清单继续引用原有未变向量，不复制全库。旧条目在保留期内留存供回退。
6. 核验候选完整清单、实际向量ID、维度/模型指纹及内容输入哈希后，短事务复查目标资料版本和项目状态，切换活动MD快照与片段清单。耗时计算不占数据库写事务。
7. 任一阶段失败不改变当前已启用版本。构建中编辑、删除、恢复等使快照过期时，候选失效并合并排队最新目标；不能无限重复提交过期任务。
8. 全量重建建立独立新集合，全部重算，不用缓存伪装“全量”。验证成功再切换；旧代际仍可回退。

检索只查询当前活动清单允许的向量，并在返回后核对知识库/文档删除和启用状态；不能先从包含历史条目的全集取topK再过滤，导致有效新资料被旧条目挤掉。物理向量仅保存不可变信息；名称、页码、启用状态从SQLite当前清单回填，避免向量共享时元数据串版。

后台维护SQLite任务/outbox与向量清单；崩溃恢复须核对阶段与实际写入。成功写入但尚未激活的向量可重复利用或标记未引用，不当作活动资料。多个上传批次按知识库合并索引任务，避免每文件触发全库构建。

显示新增/替换/移除片段、复用/新算向量数量、耗时、失败原因和最后成功时间。全量与增量接口及任务类型必须明确，不能仅做两个不同文字按钮。

## 6. 召回优化设计


### 6.1 默认流程与可选精排边界

首版实施不新增大型模型的混合召回，保留现有BGE-M3向量模型和本地服务。查询处理采用可解释的规则与可维护别名词典，不为每次提问再增加一次云端大模型改写。

本地reranker是后续可选增强：首版只定义可替换排序接口和诊断状态，不下载权重、不新增常驻精排进程、不出现“精排已启用”的假状态。启用增强前必须固定模型/精度与输入处理版本、验证本机运行和许可、评测冷启动/内存/P95及准确性，经确认后再安装。

启用后reranker仅处理融合后的有限候选，不扫描全库；失败、超时或模型不可用时回退已完成的融合排名，并在诊断中显示降级原因。重排配置变化不触发文档重新embedding。候选ID/修订必须保持映射，不能将评分误配到其他片段。具体模型、截断规则、批量和超时由后续精排专项方案确定，不阻塞首版。


```text
当前问题/必要上下文
 → 保守查询规范化与主题/实体保留
 → 向量召回 + 全文BM25召回 + 必要的精确字段匹配
 → RRF融合与重复候选合并
 → 排序接口（首版使用融合排名；后续可启用本地reranker）
 → 去冗余、补充必要相邻上下文
 → 按完整内容单元和预算选片
 → 携带来源交给现有回答模型
```

### 6.2 查询、全文索引与版本一致性

- 使用当前问题为主，只有存在指代或不完整提问时补充同主题上下文，避免无条件拼入上一道无关问题。
- 保留原始query；别名词典仅增加候选表达，不擅自替换人名、URL、编号及技术术语。语音同音误识别作为可追踪的候选扩展，不声称能可靠自动纠正。
- 引入真正的全文召回，优先评估当前Node与打包Electron的SQLite FTS5能力，并用一致的中文预分词/英文技术词处理。不要把默认英文分词器直接当作中文支持已完成；如运行时不满足要求，需在实施计划中明确本地倒排实现的替代方案。
- 标题路径、正文分字段检索，标题权重可配置。BM25统计基于该知识库当前有效修订，不跨库、不把历史条目算进日常相关性统计。
- 稀疏索引与向量共用片段ID及目标快照；候选全文记录未激活前不可见。切换时两路指向同一已启用修订。查询必须在候选截取之前限定项目、启用模式、删除状态和当前代际，避免旧记录占据topK。
- 全文索引也属于派生数据。增量更新只处理变化，删除立即排除；重启/半写入可核对，不能出现向量已更新而关键词仍命中旧正文的混合状态。

### 6.3 候选与上下文策略

- 初始评测参数：向量top40、BM25 top40，按片段ID合并并保留各路原始排名后做RRF（起始常数k=60），保留top20；最终通常选4–8片，受6000字符预算约束。这些是实验起点，不承诺比当前24/6更好，不单凭扩大数量验收。
- 查询精确人名/编号/错误码/URL时，用完整实体匹配提高对应候选优先级；不继续累积只针对某一位老师的特例规则。跨文档问题允许多个来源，不一刀切限制每篇最多一片。
- 固定0.45门槛改为可配置、按标注集校准；不同模型、BM25与rerank分数不能当成同一尺度直接比较，也不能展示为“回答正确概率”。低证据时明确知识库依据不足，不通过填满片数掩盖。
- 同修订重叠片段按内容与范围合并，避免6片几乎都是同一段。需要时仅补充同章节相邻片段/表头/定义，且计入最终预算，不能一次扩成整篇。
- 上下文按句子、列表、代码或表格的完整单元组装，超预算先舍弃低价值候选，不直接按字符截断破坏结构。6000字符是首版装配预算，后续若改token预算需明确所用计数器及模型上限。
- 不根据标点或词数任意丢弃短问题；异常query和无文本截图按明确策略处理，图片理解/OCR query提取属于可选后续能力，不能把现有截图向量检索描述为已支持。

### 6.4 失败、无答案与降级

- 两路正常时使用融合结果；某一路确实服务失败可使用仍然有效的另一路，显示降级状态，不把失败称为“零命中”。取消和总请求期限覆盖各阶段，不能无限等待。
- 指纹不匹配、索引代际缺失等一致性错误不能用旧向量强行继续；若稀疏路仍有经过校验的当前有效证据，可明确降级使用稀疏路，否则报索引异常。
- 两路都失败不伪装成“知识库没有答案”；两路成功但没有足够证据才报告“依据不足”。是否调用现有通用回答模式遵循现有设置，不冒充基于资料回答。
- 查询过程中删除/禁用资料或项目，返回前再次过滤，不使用过期缓存；必要时减少片数，不能补入无关内容凑数。

### 6.5 可观察与评测

检索测试增加可展开的诊断：实际query、使用上下文/别名扩展情况、各路候选数量及排名、融合排名、精排是否启用、去重/过滤原因、最终上下文、页码/章节及各阶段耗时。不同分数分别标注，避免展示一个无法解释的混合分。

复用现有20题作为历史基线，并补齐精确网址、人名、近义表达、语音误识别、跨片段、跨文档、无答案及多轮指代样例；在固定语料/活动修订和模型下人工标注支持答案的片段。20题仅作小样本回归，调参题与验收题分开。

分别测量候选Recall@20、最终上下文证据覆盖、MRR或nDCG、来源正确性、无答案误召回、P50/P95延迟与本机资源；在相同生成模型/提示词下另测回答准确率和忠实度。比较当前方案、真实混合召回、可选reranker的消融结果，报告每题证据和失败例，不预先许诺准确率提升百分比。

模型指纹/维度探测按模型摘要缓存，不能每次提问无必要地再算一条诊断向量；query缓存以活动代际、模式、规范化query和检索配置为键，删除/禁用必须立即失效或在返回前复核，不能为了提速返回已失效内容。

首版召回优化的上线条件：旧功能与隔离检查通过；最终证据覆盖改善且无明显无答案误召回退化；提供实时场景的延迟与资源报告。未达到时保留可回退配置，不仅凭平均分覆盖当前方案。可选reranker启用另需比较精排前后的消融结果，经确认后再安装，不作为首版上线前置条件。

## 7. 知识库删除与恢复

采用“移入知识库回收站 → 可恢复 → 明确确认后永久清理”的生命周期，删除按钮作用于整库，不等同于当前资料行的移除。

- 独立知识库：菜单提供“删除知识库”，展示资料数量和影响，确认后软删除。
- 内置 Shiping 资料库：为桌面集成保留固定容器；提供“清空资料库（可恢复）”，隐藏和禁用当前资料，不留下失效桌面引用。这是本Spec建议行为。
- 删除事务立刻标记项目不可检索、隐藏入口，增加状态版本，撤销待执行任务与正在构建任务的发布资格；运行中的OCR可请求取消，不能在完成后重新激活。
- 项目已删除时旧收藏链接/API不得继续访问其正常资料或返回命中。只允许通过明确回收站恢复/导出接口访问。
- 恢复项目不自动恢复其中原先单独删除的文档；模式选择保留，向量缺失则补建。
- 永久删除需第二次明确确认；只处理此项目引用的源文件、MD修订、任务与向量。共享资产、共享embedding缓存、其他项目集合不得连带删除。
- 历史集合归属必须有登记，不能仅凭名称前缀批量删除。远端向量删除失败保留待清理状态并可重试，逻辑隔离仍有效。
- 本次不增加按时间自动永久清理。空间回收显示预计范围并人工执行。

## 8. 前端精简

取消主导航“处理与清洗”以及资料行的日常“处理/清洗”按钮。正常上传不再要求“保存并确认”“建立候选索引并启用”。

主要入口：

- **资料库**：知识库选择、上传、新建MD、搜索、资料状态、查看/编辑MD、原件和MD下载、资料回收站；知识库菜单包含删除/清空与恢复入口。
- **检索测试**：问题、命中片段、对应MD章节及真实来源位置。
- **任务与索引**：后台处理记录、失败重试、全量重建/增量更新、任务统计和历史版本。上传进度在资料列表也可见，不必到此页完成日常流程。
- **设置与维护**：服务状态、备份恢复及高级集合信息，合并当前重叠维护入口。

单份资料显示：排队中、解析中、清洗中、待索引、索引中、已就绪、需处理、失败、已取消。更新现有资料时同时显示“当前版本仍可用 / 新版本处理中”。

异常详情复用现有报告能力，但以“问题与处理”为入口，提供具体页码、原因、重试/输入密码/修改MD/显式排除页及理由。查看原文/清洗摘要是可选信息，不再成为每次上传的必经页面。

所有外来Markdown和HTML表格渲染必须过滤脚本与危险URL，禁止执行原始HTML脚本和自动加载外部资源；本机文件下载只能通过受控资源接口，不暴露任意文件路径。

## 9. 代码整理与数据演进

保留共享解析器、OCR资源、防护上限、原件与修订、SQLite事务、当前结构分块与检索融合算法；以统一服务协议替换多处业务调度。

拟收敛模块：

- ingest：原件接收、检查、解析/OCR。
- markdown：格式转换、清洗、规范化、来源映射。
- indexing：分块、差集、向量缓存、全量/增量任务与发布。
- retrieval：查询规范化、FTS/BM25与向量召回、融合、去重、上下文装配、诊断；精排接口可扩展。
- library：知识库/资料/修订/回收站与备份。
- api：本机统一命令/查询接口，桌面与网页共用。

SQLite增加项目删除版本、草稿/已启用修订指针、canonical MD修订、规范化/分块配置版本、片段—向量映射、全文派生索引与统计、检索配置版本、任务租约/outbox、集合归属与清理记录。复用已有表并做版本迁移，不为改名再复制一套资料。

迁移原则：

1. 完整备份并验证恢复，保留全部资料ID、标签、模式、回收站和人工编辑。
2. 既有确认正文直接转换为canonical MD；不自动重跑原件OCR，不承诺旧正文能还原未知表格或页码。
3. MD转换后在候选索引重建，逐库验证并切换。切换前旧索引继续服务；转换失败项目保留旧可读版本并明确迁移待完成。
4. 原件缺失资料保留已有正文并提示；不得为了统一MD而删除资料。
5. 迁移完成标记后，新写入只走统一服务。旧JSON/v2/v3读取路径移入迁移工具，不长期保留在日常CRUD分支。
6. 旧集合与备份在核验后仅列出清理预览，本次重构不静默永久删除。应用旧版与新数据库不保证兼容，回退需恢复同一时点备份或导出增量，不能仅替换app。

本轮不改变生成模型、语音服务和回答提示词；召回参数按第6节单独评测调整；不添加云端OCR、自动语义改写、大型公式/表格模型、多人权限或公网部署。暂不宣称本次架构重构能提高回答准确率，须另外测量。

## 10. 验收标准

1. 上传支持格式，无需任何清洗/确认/索引按钮，正常样本最终可检索；重命名/元数据变化不发生无必要embedding。
2. 失败或质量异常不得静默作为完整资料启用；新资料不参与检索，更新资料保留已启用版本。所有源页有记录，来源未知明确显示未知。
3. 所有embedding任务都能追溯到canonical MD修订，无解析器直达向量写入的旁路；下载MD与索引使用内容一致。
4. 同内容重复上传不新增逻辑副本、不重复计算。编辑局部正文时，未变片段的embedding调用与向量写入数均为0，变化数量可核验。
5. 增量无变化时新算向量=0、写入=0；删除立即不能命中；模式/标签变化不重算；全量则对全部有效片段重新计算并独立构建。
6. 模型/维度/规则不兼容明确转受控重建，不能混用向量；并发编辑/删除、索引半失败、服务崩溃重启均不发布过期内容。
7. 删除/恢复/永久清理知识库不影响其他库；内置库清空后桌面可继续使用；历史缓存不泄露已删除资料。
8. 桌面与网页显示同一任务和资料版本；同版本并发修改仅一方成功；后台只有一个项目写任务。
9. 固定合成样例与现有课程样例验证MD标题、代码、表格表头、数字、URL与来源位置。分别记录召回和回答评测，不将“接口成功”当作准确率。
10. 迁移数量、正文/MD哈希、模式及回收站逐条核对，恢复演练通过；资源超限/损坏/密码/取消可见。
11. 更新安装说明、后台依赖、操作台账、备份/恢复和卸载说明。发布和pcworkspace同步前检查用户修改，排除原件、DB、模型与密钥。

12. 默认检索确实走向量与全文两路；中文实体、技术词、URL/编号可追溯到正确支持片段，诊断展示各路排名和最终上下文。
13. 候选去重及相邻扩展不越库、不越修订，表头/代码/句子不被预算直接截断；无答案和服务故障可区分。
14. 当前方案与新混合召回在相同语料、模型、提示词和保留验收题上对比；最终证据覆盖改善且无明显无答案误召回退化，延迟和资源有报告。
15. 默认没有新增reranker模型、依赖或后台精排请求；若未启用，诊断显示未启用。首版不以未经实测的准确率百分比作为承诺。
